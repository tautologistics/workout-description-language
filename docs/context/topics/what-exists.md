# What exists

What is built and working. Read it before building something again; update it
when something lands, and take the same thing out of
[tasks/deferred.md](../tasks/deferred.md) or [tasks/current.md](../tasks/current.md).

| | |
|---|---|
| **Format** | Parser, canonical formatter, validator, timeline compiler. 190-workout corpus round-trips. Alternatives: `A or B`, `A/B`, `A|B`, and a `choice:` block. Rx by division: `(women 105lb / men 145lb)` or `(105/145)`. |
| **Interop** | Import: `.zwo`, `.erg`/`.mrc`, FIT. Export: those plus Garmin Connect JSON. Verified against a real watch. |
| **Registry** | 3109 movements merged from five sources, **129 in the generation pool**, 2972 with muscle data, 125 carrying the `wdl-curated` source. Every record names its sources and keeps their claims separately. What the corpus holds is restated on every rebuild by `scripts/describe-corpora.mjs`, into `registry/SOURCES.json` and the `SOURCES.md` table — those two are the live figures; this row is a summary and can lag them. A name two records answer to is decided by ranking an **explicit alias above a record's own id** — a curator's claim on a contested spelling beats an imported record named after it — and a name no rule can decide comes back `ambiguous` rather than resolved. `node scripts/check-aliases.mjs` lists the ones left and who wins — **one**, as of the `Air Bike` split on 2026-08-23; it was fourteen when the ranking landed. Two records the same movement are merged by `sameAs` on a curated record, and — since the same date — one record holding two movements is split by `NOT_WHAT_THE_NAME_MEANS` in `scripts/build-movements.mjs`, a table keyed on `source:upstream-id` that names the record a source's entry actually belongs to. Both fail the build loudly if they name something no source produced. |
| **Analysis** | Muscle attribution with a closed 19-muscle vocabulary; per-muscle volume; ordering with the repeat-wrap. |
| **Goals** | Five rules — `no repeat`, `cover`, `limit`, `balance`, `progress` — in a separate file. `wdl goals`. Six dimensions: `movements`, `exposures`, `reps`, `seconds`, `metres`, `calories`, and since 2026-08-23 **`load`**. |
| **Generation** | `?` holes in a template, filled to satisfy the goals. `wdl generate`, single workout or a whole block. The pool it draws from is curated — see below. |
| **Programs** | An ordered block with slots. `wdl program`. |
| **Grammar** | A normative Ohm grammar in [spec/grammar-0.1.ohm](../../../spec/grammar-0.1.ohm) covering **every kind of line phase 2 reads** — step, block header with its comma modifiers, rest, score, `on cap:`/`tiebreak:`, directives, title, variants — as nine start rules over one shared lexical layer, carrying no semantic actions. What each production *means* is one module per area under `packages/core/src/grammar/`, all put on a single semantics object by `parser.ts`. It runs on `ohm-js`, vendored into `src/grammar/vendor/` and imported by relative path. *Since 2026-08-28* the compiled grammar is also readable — `WdlParser.grammar` — so a consumer can enumerate rules rather than only match against them; `src/block-affordances.ts` uses it to derive the builder's block-header modifier menu from the `blockModifier_*` cases, kept in step by `test/block-affordances.test.ts`. |
| **The parser is the grammar** | *Since 2026-08-15 (queue item 0a).* `parse.ts` matches these rules and walks them, in Node and in both apps; the regex chain is deleted. The grammar text reaches the core through the same `provide()` seam as the registry — `node.ts` reads the file, a browser fetches it, and `required('grammar')` throws by name if nobody hands it over. `parse.ts` is **306 lines and 18 regex literals**, down from 548 and ~101, and every regex that remains is *dispatch*: which kind of line this is, which phase 1 does not answer and the grammar deliberately does not either. What is still hand-written is the **assembly** — which score an `on cap:` qualifies, which variant a field belongs to, which block a child belongs to, and the `parseNode` dispatch itself. Those are questions about several lines. *Since 2026-08-28* that dispatch also strips a decorative leading `- ` from the one-line inline-body block forms (`- work 20s: Pull-Up`, `- min 1: …`, `- every 1min: …`), which previously lost the block to the step branch with no diagnostic — the inline-body extension of the 2026-08-15 "wins on the colon" rule. A *follow-up the same day* makes the **general** one-liner (`AMRAP 3min: 10 Push-Up`, `for time: 50 Burpee`, `21-15-9: Thruster`) — which has no rule and stays a movement-named step — **reported** rather than silent: the dispatch probes the text before the colon and, if it is a recognized block kind, says the header opens a block whose body belongs on the next line or in braces. |
| **Unknown is a place, not a gap** | *Since 2026-08-15 (queue item 0d), and it is what the whole grammar exploration was for.* Text the language does not read is held in `Step.unknown` / `Block.unknown` — **held, round-tripped, inert, and reported**. Kept apart from `notes` (which is rendered and which an exporter reads for a role or a ramp) and from `flags` (which the language defines); `wdl fmt` writes it back, after the modifiers that were understood; it never reaches the timeline, so no cue, no export and no analysis can act on it; and `validate` reports it as a **`note`** — a fourth severity that claims nothing. The `note:` marker on an authored note became load-bearing the same day: a bare phrase after a comma now means *unrecognized*, so canonical output writes `note: "…"` for anything the grammar would not read back as a note. Stated in spec §11.1. |
| **`3 RFT:`** | *Since 2026-08-16 (queue item 0f, first half).* `3 RFT:` is `3 rounds for time:` and reads as exactly that block — same type, count, `rounds` flag and score, so nothing downstream learned an abbreviation. One grammar production fusing the round word and the score, because the `for time` is inside the abbreviation; `AMRAP` and `EMOM` were already in on the same grounds, which is that what a gym writes on a whiteboard is a spelling the language reads. Canonical output writes the **long** form — `RFT` is the same words shortened rather than a different word for the structure, unlike `rounds` vs `sets`. A **bare** `RFT:` is declined on purpose and stays reported, since it names rounds without saying how many and there is no unbounded repeat to read it as. Spec §5.2. `TABATA` is still unread and is a structure to define rather than a header to abbreviate. |
| **Order is free on a header, kind included** | *Since 2026-08-16 (queue item 0f, second half).* A block's **kind** — what it is: `3 rounds`, `21-15-9`, `AMRAP 12min`, `team of 2` — may be stated in any comma position, so `for time, 3 rounds:` and `3 rounds for time:` are one block with one tree. Until then a kind after a comma was read as text nobody taught the language, and `for time` made that quiet rather than loud: it parses alone, so the block ran **once** instead of three times. The fix is the general rule and not `for time` — `blockKind` is split out of `headerKind`, leaving the match-anything `headerName` behind so `unknown` stays reachable after a comma, and `blockModifier` reaches it too. Two boundaries come with it: a header states **at most one** kind (a second is a contradiction, so the first stands and the second is held verbatim and noted), and an unreadable head with a readable kind after it (`cap 12min, 3 rounds:`) is still *reported* and is written back in front of the kind. Spec §5.0 and §11.1. |
| **An interval states its bound, and every one of them round-trips** | *Since 2026-08-16.* A clock-driven repeat may be bounded by a count (`every 3min x 5:`), by a window (`every 90s for 12min:`, new), by failure (`every 1min until failure:`), or by nothing at all (`every 90s:`). A window in whole minutes is what `EMOM` spells, so `E2MOM 20min:` is canonical for it and `EMOM` is its one-minute case. Two of those four were **unwritable by `wdl fmt`** until this landed — it emitted `every 1min30s x undefined:` and `every 2min for 20min:`, neither of which any rule read — and since an unreadable header is held as a named sequence, each was a stable round trip that had silently lost the clock. Spec §5.5. |
| **Partner rotation** | *Since 2026-08-15.* `partner rotation:` — two athletes, two pieces of work at once, then they swap, so both do both. Its own block kind rather than a `team of 2` qualifier, and holds **exactly two**: with two athletes a third has nobody to work alongside, so `validate` reports `partner-rotation-arity` as an error. The timeline warns instead of computing a length (a step is bounded by the work beside it, not by its own count) and the block is `freeOrder`, since the two athletes take opposite orders. Spec §5.11.1. `team of N` is untouched. |
| **A file that was never indented still reads** | *Since 2026-08-15 (queue item 0b).* A block adopts what was written flat under it, and `wdl fmt` writes the indentation back — forgiveness at the **input** edge, with the at-rest format unchanged. Four rules, stated in spec §2: an *empty* block adopts whatever comes next, block or not, because empty it cannot be anyone's sibling; once it has content a plain line cannot close it, since a step is not a container; a **block header** closes it only if that header is flat too, so a block that indents its own body inside a flat run is *in* the run; and a `score:` line is never adopted, because a score is a statement about the whole. Phase 1 keys on the trailing `:` and nothing else, so it stays free of WDL knowledge; rule 4 is phase 2's. A header landing where its indentation did not put it is reported as a `note`. A file that *did* indent is untouched — a dedented line there is a deliberate one. |
| **Tests** | 2020 passing, 1 pending. `vocabulary.test.ts` covers 395 documented forms, pinning both the canonical text and the *interpretation* — the tree — for each; `corpus.test.ts` round-trips 190 real workouts and `golden.test.ts` pins how each of them is *understood* — shape, seconds, cap, pacing, totals, volume by movement and, since 2026-08-23, **load by muscle**, which is the half a registry merge moves and the only half that is a property of the record rather than of the text; `workouts-canonical.test.ts` (since 2026-08-29) re-runs the `registry/workouts.canonical.json` deriver in process and pins that committed file, one assertion per corpus workout modulo the `generated` stamp — the guard `interpretations.json` and `vocabulary.json` already had and it did not; `grammar.test.ts` feeds every line of every kind the project has to the start rule for its kind, in six separately-counted areas — **844 step lines, 248 block headers, 60 rests, 43 scores, 11 directives, 204 titles** — lists the ones it cannot read with a reason each, and asserts the rules that used to be visible only as a disagreement with the old parser; `variants.test.ts` covers the two spellings of a division — what each resolves to, and a reparse compared **field by field** rather than text to text; `result.test.ts` covers the record, the instantiation it produces, and a load ramped across a series of them; `portable.test.ts` fails on any specifier under `src/` that a browser could not resolve. `generate.test.ts` pins the **pool** as a property of the registry rather than of the search — that every member was judged by somebody, that every curated record is in it, that its size is 129, and that nothing in it is warm-up or mobility work. They answer different questions; see [lessons-learned.md](lessons-learned.md). *As of queue item 0e, 2026-08-15, only **one** line the project writes is unread by any rule (`10x Curl`) and only one pinned reading is known-wrong — the same line.* |
| **Divisions** | *Since 2026-08-18 (queue item 1).* A step's rx split and a workout's `variants:` table are one namespace with one resolver, `packages/core/src/variants.ts`. `divisions(w)` lists what a workout offers whichever way it was written; `resolve(w, name)` returns the workout that division reads, applying a split step-precisely and a `variants:` entry by movement — matched through the registry, so `wall-ball:` finds a step written `100 Wall Balls`. `--variant <name>` hooks in once and reaches `fmt`, `check`, `timeline` and `export`. A value may be a load, a load and a height, or a movement to swap in; anything else is reported by name and the step is left alone. **With no division chosen a step reads as its at-rest text** — `30 Clean & Jerks (women 105lb / men 145lb)`, both magnitudes, labelled — which is the state the builder is permanently in, and the reason an rx load is visible there at all. Spec §10.1. |
| **A division is chosen on the board** | *Since 2026-08-20 (queue item 1a).* A workout that offers one shows a picker in the board's footer, built from `divisions()` in its stable order, with *as written* first; a workout that offers none shows no control. Choosing re-cues from `resolve()` **from where the reader stands** — the cursor, the workout clock, the section clock and the lap count all survive, because a reader who says "women" three rounds in is answering a question about the weights, not asking to start over. **The choice rides in the hash beside the workout**, so it survives a reload and travels with the share link: `#<workout>&division=women`, and `encodeURIComponent` escapes `&`, so no workout text can forge the separator and every link written before it reads unchanged. `validate` runs on the workout the division reads, which is what `wdl check --variant` does, and a resolve diagnostic joins the strip whatever its severity — a `note` there says a step did *not* take the division asked for, which is the silence the control exists to prevent. **Nothing rewrites a line.** The rows go on saying what was written, because in both spellings the line already shows every division at once — the board shows the class and the bar shows the face of it you are doing. **The builder is deliberately excluded**; see [builder-ux.md](builder-ux.md). |
| **Results** | *Since 2026-08-23 (queue item 2).* A second record type, `.wdlr`, in the same line grammar as a workout, a goals file and a program: `packages/core/src/result.ts`, spec [results-0.1.md](../../../spec/results-0.1.md). A workout is a **class** and a result is an **instantiation** of it — one athlete, one date, the weight actually on the bar. The head names what the record is *of* (`result: crossfit:fran`, any unique string with an optional namespace, **never derived from content**), and a `snapshot:` holds the workout text **verbatim** so the record survives the file being edited or deleted and doubles as the version record. `instantiate()` produces the execution: the division resolved first, because the author wrote both weights into the file, then the recorded loads over the top, because what you lifted is the number true of you. Loads are matched to steps by movement through the registry — the same machinery `variants:` uses, now shared rather than copied. `wdl result` checks a record against its own snapshot: a division it does not offer, an id that disagrees with it, a load for a movement it does not contain, a score whose shape is not what it declares. `--goals` reads the records as one series, **in date order as text** — an ISO date sorts as a string, so nothing constructs a clock. Each CLI verb now states what its file arguments are, so `wdl fmt -w` on a `.wdlr` refuses instead of parsing a training log as steps and writing the mangling back — every other record here is recoverable and a log is not. |
| **`measure: load`** | *Since 2026-08-23 (queue item 2), and the reason results were the largest piece.* `Dimension` gains `load` and `Exposure` gains a load in kilograms, so "ramp the squat week over week" is finally a question something can answer — asked of a series of **results**, since the weight on the bar is a fact about an execution. Three things make it unlike every other dimension, each stated in the spec: it is the **heaviest, not the total** (three sets at 100kg is not 300kg of anything, and §9.1 already reads `score: load` as "heaviest successful"), rounds never multiply it, and it is counted in **kilograms** so a bound written `10lb` converts. A percentage load contributes nothing — that is the original objection kept intact, since `85% 1RM` needs an athlete profile — and so does an unlabelled magnitude. A `progress` rule that finds no load **anywhere** in the series reports that rather than passing on two zeroes. |
| **The pool is what somebody judged** | *Since 2026-08-23 (queue item 4).* `core` — the set `wdl generate` fills a `?` from, and the set the builder's palette shows with an empty search box — is no longer a score threshold. It is the three signals that are a **judgement**: a workout in our corpus writes it, the curator wrote a record for it in `registry/movements.json`, or a vendor tracks a 1RM for it. Sources agreeing, heading a family and absorbing duplicates are facts about *catalogues and names*; they still score, the score still cuts dedup, and they no longer put a movement in front of a reader by themselves. **178 → 129**, then 128 once the alias pass landed beside it (an alias-only curated record says nothing about the movement, so it no longer counts as the curator having judged it work — see the header of `scripts/mark-core.mjs`), then back to **129** on 2026-08-29 when the `Pec Deck` curation folded `Butterfly` / `Butterfly Machine` / `Machine chest fly` into one curated record that does make a claim about the movement. The threshold went too, because curation is +3 against a bar of 4 and so could never carry a record alone — fourteen hand-written records were out, `Bar-Facing Burpee` and `Squat Snatch` among them, while `Smith Machine Close-Grip Bench Press` was in. The 77 records the old rule admitted on catalogue evidence alone had, every one, **no `pattern`**: `? squat` could not reach them, so they were reachable only by being picked blind. **Nothing left the language** — a movement out of the pool still validates, still analyses, and the palette still finds it the moment you type. Eight records were curated in to fill real holes: `Barbell Row`, `Inverted Row`, `Ring Row`, `Romanian Deadlift`, `Sumo Deadlift`, `Chin-Up`, `Step-up`, `Russian Twist`. |
| **A load can be a word** | *Since 2026-08-23 (queue item 6).* `heavy`, `moderate`, `light`, `unloaded` are a fifth `Load` kind, `qualitative` — `@ heavy` on a farmer's carry or a KB swing reads as a real `Load` target, not raw text, the same way `85% 1RM` or `of heavy-single` do. It carries no kilograms and never will (`loadKilograms` returns `undefined` for it, same as an unresolved percentage or reference), so volume, `measure: load` and export are unchanged. What moved is visibility: anything that walks `targets` for `t.kind === 'load'` — `heaviest()` in `muscles.ts` among them — now sees a qualitative load and can say "loaded, not resolvable" instead of missing it entirely, the way a raw target always did. Spec §3, §7. |
| **A cap is a bound, and a duration is a length** | *Since 2026-08-23 (queue item 3).* `Timeline.cap` and `Run.cap` say the most a workout may take; `estimatedSeconds` and `totalSeconds` say how long it takes; neither is ever filled in with the other. A capped for-time workout has the second undefined, because an athlete who finishes Open 25.2 in eight minutes took eight and not the twelve they were allowed — it used to report `duration: 12:00`, the AMRAP `window` conflation one step along. The builder and `wdl timeline` print both rows, `duration: athlete-paced` and `cap: 12:00 at most`. **The rule is not about caps but about what ends the work.** A bare `AMRAP:` under a cap runs until the clock stops (spec §5.6), so `77-tiff.wdl` ends *at* twenty-five minutes and that is a real length: `fillsTheClock()` in `timeline.ts` asks that one question, and both numbers are set for exactly that shape. A cap counts only on the **spine** — an only child of an only child, up to the root — the same rule as the window, so a capped section between two others caps that section and not the workout. `wdl export --to connect` hands the cap over as `estimatedDurationInSecs` where there is no length, since Connect has one field and nowhere to say "at most". |
| **Apps** | Builder and board, both in a browser over the same core. The builder has a movement palette with muscle filtering, drag-and-drop, and live goal checking; goals can be written, saved and downloaded from it. *Since 2026-08-28* the palette also carries a **repertoire of hand-composed movement sets** — build a set by dragging movements onto it or by a checklist "compose" mode, reorder/rename/remove within it, drop a whole set into the outline in one click, and export/import the repertoire as a plain JSON file (`localStorage` stays the live store); see [builder-ux.md](builder-ux.md). Each outline row carries a `»` caret for **what that line can take next** — on a step row, the modifiers its movement supports (from the registry); *since 2026-08-28* on a block-header row, what that header can take (from the grammar): a duration to finish a bare `AMRAP:`/`EMOM:`, and the comma modifiers `blockModifier` allows (`cap`, `for time`, `as …`, `wearing …`, overrun, an inherited `@` target), each spliced in as an editable default — including on inline block rows (`work 20s: Pull-Up`) and, since the 2026-08-28 parser fix, dashed ones. The board loops the *section* that repeats, on that section's own clock, lets a division be chosen on it, and **writes down what happened** when the session ends. |
| **A body map, front and back** | *Since 2026-08-23 (queue item 7).* `apps/shared/body-map.js` — one stylised SVG path per muscle, id-matched to `registry/muscles.json`'s 19-muscle vocabulary, front and back, shared by both apps. Draws nothing itself: `aggregateStates`, `highlightStates` and `heatStates` are pure functions from what `exposures()`, `musclesFor()` and `muscleLoad()` already report, so the map cannot drift out of step with the vocabulary — an id the SVG does not carry is simply never painted. **Primary vs secondary is opacity, one colour per layer** — full for a primary mover, ~40% for a muscle a step only assists — settled over two colours because the aggregate and the highlight already need a colour each, and a third axis of hue for primary/secondary would have meant naming eight colours instead of two; see [settled-decisions.md](settled-decisions.md). Four views: the **builder's aggregate** (opacity by primary/secondary, whole workout), **hovering a movement in the palette or the outline** against it (the movement's own colour over a dimmed aggregate — "what this adds", not "what this does"), a **heat map** toggling between `frequency` (exposures, always defined) and `volume` (reps, hatched rather than coloured cold where a muscle was worked only by a carry, a hold or a max effort — `stepVolume` reads those as zero reps by construction, and colouring that cold would say "not worked" and lie), and the **board's header**, the same aggregate/highlight pair driven by the cue cursor instead of a hover. The board's `canonicalMovements` fetch — previously lazy, paid only when a `variants:` value needed resolving — is now eager but not awaited, since the map wants an attribution for every cue of every workout; see [known-debts.md](known-debts.md). **Updated 2026-08-24, twice, both from driving it rather than from the queue.** First, the shapes: the original hand-drawn blocks were replaced with real anatomical regions adapted from **body-muscles** (github.com/vulovix/body-muscles, Apache-2.0 — `apps/shared/vendor/body-muscles-NOTICE` and `-LICENSE`), chosen over two other candidates found the same way — `react-native-body-highlighter` and `MuscleMap` — because both of those are missing an explicit `lats` region and a distinct `abductors` one, where this source covers all 19 directly with only two judgement calls (`mid-back` from its `spine` region, `abductors` by splitting `gluteus-medius` out of its combined glute grouping). Second, the map is small on purpose (legible at a glance, sized to sit beside the rest of the page) but a small anatomical figure is hard to read in detail, so `attachZoom()` makes every mounted map clickable (and focusable/Enter-able) to open a full-size copy in an overlay — `link()`ed to the small one internally so a live repaint (a hover, a step forward on the board) keeps reaching the overlay instead of freezing it at the moment it opened, and the overlay swallows every keydown but Escape so the board's own space/arrow-key handling can't advance the workout while someone is just looking at the map. |
| **The board's footer can scroll off the bottom of a short screen** | *Fixed 2026-08-24, caught by driving it at phone height.* `body` set `min-height: 100dvh` rather than `height: 100dvh` — a floor, not a ceiling — so on a workout tall enough to exceed one screen, content stretched the body past the viewport instead of `.board`'s own `overflow-y: auto` doing the scrolling, and the footer (Start/Next/Back/Reset, the position, Edit) went with it, reachable only by scrolling the whole page. One property. With it, `.board` is the thing that scrolls, the header and footer stay put, and the existing per-cue `row.scrollIntoView({block:'nearest', behavior:'smooth'})` in `paint()` — unchanged — has a real bounded container to scroll within instead of nothing to do. *Touches: `apps/display/board.css`.* |
| **The board writes the result** | *Since 2026-08-23 (queue item 2).* It held the clock and the cursor, so it is the only thing that can. It records **only what it observed** — the time, the splits, and how many rounds closed where the workout is scored by them — and leaves what no clock can see as a line to type, with the loads the file states offered as commented-out hints; inventing a plausible number there would be software making something up about somebody's training. The panel opens on finishing and by a **Result** button any time after a session has begun, since a workout you stopped halfway still happened. Output is the format's own text, editable before it is kept, downloadable as `.wdlr`. **A split is a line you have already been on** — `Cue.rounds` looks like the answer and is not, because `run` fills it only for a block that *repeats* and a rep scheme is expanded into tiers, so keying on it recorded no splits at all for Fran. |
| **The board runs the cap** | *Since 2026-08-23 (queue item 9).* `Run.cap` counts down on the board the way a cue's or a section's own clock already did — `state.cap`, read from it in `recue()`, joins them as a third candidate for the one big number, and `tick()` shows whichever of a running section's clock and the cap is nearer. `77-tiff.wdl` (`for time, cap 25min:` around a bare `AMRAP:`) is the case that needs the choice: the AMRAP has no clock of its own, so the cap is what counts down and what ends it. **Running out ends the workout where the cursor stands, not at the end of the cue list.** `capOut()` freezes the clock, disables `start`/`next`/`prev`/`leave` and opens the record panel, but — unlike `finish()` — leaves `state.at` alone: a cap did not certify the athlete reached the last cue, only that the clock did, and `measuredScore()` already reads the clock rather than the cursor for a `for time` score, so nothing about what it reports had to change. It invents no reps or rounds number either; that guess is item 2's question, on a *result*, not this one's. |
